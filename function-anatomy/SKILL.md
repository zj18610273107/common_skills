# 函数剖析

先读取仓库源码中的函数定义，不要凭记忆解释。

## CodeGraph

项目根目录 `build/codegraph.db` 是 CodeGraph 数据库。开始分析前，优先执行：

```bash
CODEGRAPH_DIR=build codegraph explore "<函数名、调用链或问题>"
```

先用 CodeGraph 结果定位函数定义、调用路径和源码片段，再结合仓库源码核对。若 `codegraph` 提示没有索引，不要执行 `codegraph init`，改用 `rg` 在源码中定位。

## 输入

- 文件路径和函数名。
- 可选：子系统上下文，例如驱动、总线、硬件。

## 函数注释分析

剖析函数之前，如果函数定义上方有注释，按下面三步分开输出，不要合并：

如果函数没有注释，跳过本小节，不输出“无函数注释”。

1. 翻译注释
   不要输出“翻译注释”“保持原格式”“不贴英文原文”等引导句；直接按原注释格式输出中文翻译，保留 `/** */` 多行结构、`@参数`、`Return` 等格式，只把英文文字替换成中文。

2. 分析注释
   解释注释中的函数用途、每个参数、返回值约定，并与源码对照。

3. 精简概括
   用一两句话概括函数功能，不重复注释原文。

## 函数功能总体概括

在函数签名之前，先用一两句话概括函数整体功能。

概括内容：

- 函数属于哪个生命周期或调用链阶段。
- 函数主要做什么。
- 函数返回后产生什么结果。

## 函数签名分析

输出函数签名时，必须保留 `__iomem`、`__user`、`__force` 等类型修饰符，不能省略。

签名中没有这些修饰符时，不写“没有修饰符”等说明，直接不提及。

这些修饰符用于 Sparse 等静态检查，控制编译器和分析工具对指针类型的检查，不改变运行时 ABI。常见含义：

- `__iomem`：指向 MMIO 映射内存，应使用 `readl`、`writel` 等访问。
- `__user`：指向用户空间内存，应使用 `copy_to_user`、`copy_from_user` 等访问。
- `__force`：显式放弃 Sparse 的地址空间检查。

分析时先保留原样，再说明每个修饰符的作用。

## 导出信息

检查函数定义后面是否紧跟导出宏，例如：

- `EXPORT_SYMBOL(func)`
- `EXPORT_SYMBOL_GPL(func)`

如果存在，必须保留原格式输出，并说明：

- 导出到内核符号表的函数名。
- `EXPORT_SYMBOL_GPL` 的含义：只允许 GPL 兼容模块使用该符号。
- 没有导出宏时，跳过本小节，不输出“未导出”。

## 输出结构

1. 函数注释分析（如果存在函数注释）。
2. 函数功能总体概括。
3. 函数签名（保留并解释 `__iomem`、`__user` 等类型修饰符）。
4. 导出信息（如果存在 EXPORT_SYMBOL / EXPORT_SYMBOL_GPL）。
5. 参数：类型、来源、含义、生命周期。
6. 局部变量：类型、含义、生命周期。
7. 按下面的模板逐个分析函数调用。
8. 调用链角色：拿资源、分配、注册、保存、初始化、清理、回滚。
9. 错误路径和配对操作。
10. 一句话总结。

## 函数调用分析模板

对每个函数调用，必须说明：

- 函数功能：用一句话简单概括这个函数做什么，不展开参数、生命周期和配对。
- 函数名拆解。
- 每个参数的含义。
- 返回值与失败约定。
- 生命周期和所有权（devm_、alloc/free、get/put）。
- 配对操作（enable/disable、register/unregister、probe/remove）。
- 在调用链中的位置。

## 规则

- 先解释参数，再解释行为。
- 先找出调用者，以及每个调用操作的对象。
- 错误路径按成功设置的反向顺序追踪。
- 用周围的检查确认返回值约定，例如 if (!ptr)、if (ret)、IS_ERR、PTR_ERR。
- 输出结构中，函数没有对应内容时跳过该小节，不写“无”“没有”“未导出”等说明。
- Linux 内核代码优先参考常见模式文件。
